# Project workflow

These instructions apply to contributing to this repository. For installing the published package into another app, read [the setup skill](packages/jev-devtools/skills/setup-jev-devtools/SKILL.md) and follow that app's own workflow. The skill and its references ship with npm; keep them aligned with public APIs and the independent examples. [llms.txt](llms.txt) indexes the consumer documentation.

- Work on a feature branch and open a PR targeting `main` for every change unless the user explicitly requests otherwise.
- Do not commit or push changes directly to `main`. Do not merge, publish to npm, or deploy without an explicit request.
- Name every PR using `type: description` with a lowercase type: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, or `revert`. Optional scope and breaking-change marker are allowed (`fix(viewer): preserve zoom`, `feat!: change the flow API`). Use a clear description of the final change; rename the PR when its scope changes. The **PR title** check enforces this for drafts and ready PRs, including title edits.
- When creating or updating a PR, including through CLI or API tools, follow [the PR template](.github/pull_request_template.md) and [description guide](CONTRIBUTING.md#pr-descriptions). Keep the headings in order: Problem, Change, Scope and compatibility, Verification, CSS review. Explain the problem before the solution, report observed results and explicit verification gaps, and keep detail proportional to the change. Rewrite the description when scope changes so it describes the final implementation. Preserve the CSS checklist when applicable; otherwise keep its heading with "Not applicable."
- Push completed feature work with verification details, and leave the PR open for review.
- Run performance benchmarks locally, not in GitHub Actions. Do not add benchmark workflows or dispatch hosted benchmark runs.
- Keep the package independent of the playground. Consumers use public exports; do not import internal source across workspaces.
- Run `npm run check`, `npm test`, `npm run build`, `npm run check:playground`, `npm run verify:package`, `npm run verify:nextjs`, and `git diff --check` before opening or updating a PR. Visually verify UI changes when browser access is available; disclose unavailable checks.
- Add tests for observable behavior and credible regressions. Keep recorder fixtures independent of demo scenarios.
- Keep API credentials on the server. Distinguish samples from live inference. Follow official TypeSafe semantics; diagrams must not invent model reasoning or routing policies.
- Preserve third-party notices and PR-based workflow documentation when moving code.
- After changing the package version, run `npm run sync:readme-version` to update both README badges, exact-version npm links, and archive examples. CI checks and package creation reject stale README versions.
- For user-visible changes, update `CHANGELOG.md` under Unreleased in the same PR, with behavior, compatibility notes, and a PR link when available. Keep the overview table aligned; do not describe open PRs as merged or unreleased work as published. Follow `docs/releases.md` when promoting entries to a release.
- Keep generated benchmark results, CPU profiles, screenshots, logs, and per-run reports out of Git under ignored `benchmarks/results/`. Keep scripts/fixtures tracked; report comparisons, provenance, and limitations in PR descriptions or discussions. Do not force-add artifacts or copy them into `docs/`.

## Package CSS maintenance

- Every package CSS selector, declaration, custom property, keyframe, and inline style must serve a current rendered component/state or an explicit isolation, accessibility, browser-support, or compatibility requirement. Do not add speculative styles or copy unused rules from demos.
- When changing or removing markup, classes, states, animations, or style variables, audit the associated CSS in the same PR. Remove orphaned rules, unused variables/keyframes, ineffective declarations, and redundant overrides; check every branch of grouped selectors. Keep intentional fallback/cascade ordering intact.
- Trace usage through JSX, dynamically composed classes, attributes, inline styles, and JavaScript `setProperty` calls. A text-search miss or an unused browser-coverage range alone is not proof that CSS is dead: inspect interaction states, conditional/virtualized content, media queries, and pseudo-elements before deleting it.
- Keep `packages/jev-devtools/src/inspector.css` as the shared source for the embedded drawer stylesheet and public CSS export; never hand-edit generated styles. Scope internal selectors to the DevTools boundary and namespace animations. Keep app/demo styling outside the package.
- Explain non-obvious defensive resets, `!important`, fallbacks, and retained compatibility rules with a nearby comment naming the behavior they protect. Temporary exceptions need a linked issue and a removal condition; do not use broad unused-CSS allowlists or blanket purge exclusions.
- For CSS-affecting PRs (including markup-only changes), follow the [CSS review procedure](CONTRIBUTING.md#package-css-review), report usage/removal evidence and relevant browser checks, and run `npm run verify:drawer` in addition to the required checks. Add regression tests only for meaningful observable failures, not selector inventories or CSS-text snapshots.
