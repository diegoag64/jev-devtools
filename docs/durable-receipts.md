# Durable release and deployment receipts

Design recommendation for [Issue #77](https://github.com/diegoag64/jev-devtools/issues/77), investigated on October 25, 2026 against `bad7e0a3823d9d0a62b70cbfb6e4acabd6942665`.

**Proposed, not activated.** Keep the [current release completion rule](releases.md#completion-and-recovery) and [manual docs policy](docs-publishing.md#manual-publication-checklist) until the implementation and rollout gates below pass. This document authorizes no publication, permission change, or deployment. Closing the design investigation does not mean the new workflow is operational.

## Recommendation

For this repository's current mutable GitHub releases, store small, versioned JSON receipts as **append-only release assets by publisher policy**, with human-readable companion summaries. Link the release's Assets section from reviewed source. Record package publication and each later docs deployment separately, after their respective independent checks. Download and verify the stored bytes before reporting that the receipt is durable.

This removes both routine publication-record and docs-receipt PRs after a one-time tooling/policy change. Code, compatibility guidance, intended versions, and release notes still go through reviewed source PRs. Recovery that changes shipped content still needs a PR. Receipt upload is part of an explicitly requested release or docs publication, not a new trigger for either.

This is a conditional choice, not a reason to disable release immutability. Check repository settings before publishing and the actual target release before uploading. If either requires immutability, stop this storage path and use the existing record-PR process; select a separate receipt store through a reviewed design change before removing that fallback.

## Evidence and limits

Read-only GitHub API checks on October 25, 2026 found:

- `diegoag64/jev-devtools` is public. The current CLI identity reports repository push/admin access; that does not prove the permissions of a future workflow token.
- `GET /repos/diegoag64/jev-devtools/immutable-releases` returned `enabled: false` and `enforced_by_owner: false`.
- GitHub release `v0.5.2` (ID `423676848`) is published, non-prerelease, mutable, and has no assets. Its publication timestamp is `2026-10-25T21:36:35Z`.
- The deployment list exposes `npm-release` environment records. These approval/job records do not establish a GPT Sites deployment or successful live docs verification.

The checked-in release workflow has `contents: write` only in its finish job; the npm publish job separately has `id-token: write`. Release artifacts expire after 30 days. `scripts/release.mjs` writes npm evidence to `publication.json`, then verifies the tag/GitHub release without adding those observations to that JSON. The docs helper verifies inspected bytes and live content but does not persist a remote receipt.

Remote writes, credential changes, asset upload/download round trips, and deletion/recovery were **not** exercised. Those are rollout gates, not inferred from repository access. Existing npm/Sites permissions, audience, domain, and reviewer protections remain unchanged.

## Storage alternatives

| Location                                | Retention and access                                                                                                                                                                                | Fit and tradeoff                                                                                                                                                                                                                 |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repository Markdown via PR              | Reviewed, cloned with Git, retained with repository history. Existing access model.                                                                                                                 | Strong fallback and historical record, but creates the two bookkeeping PRs and cannot update the artifact that already shipped.                                                                                                  |
| GitHub release assets                   | Public reads for this public repository; managing releases requires write access. Assets have no Actions-style configured expiry, but mutable assets/releases can be deleted by authorized writers. | Recommended under the audited settings. Separate hashed files support readback and retries without editing package bytes. Requires explicit backups; this is not tamper-proof archival storage.                                  |
| GitHub release notes alone              | Public and easy to find, but editable even for immutable releases.                                                                                                                                  | Use stable links and a compact human summary. Replacing a whole body risks overwriting human edits; notes alone are a poor machine-readable event history.                                                                       |
| GitHub deployments/statuses             | Separate Deployments permissions; events can be consumed by integrations. Previous statuses expire after 90 days; the current status remains.                                                       | Useful operational pointers, not the sole historical receipt store. Creating records can emit deployment events, so it is not a harmless generic upload channel.                                                                 |
| Separate receipt releases or Git ledger | A dedicated release could be published only after all its evidence exists; a separate Git store offers history.                                                                                     | Can accommodate immutable package releases, but adds tags/releases or a repository/branch, access rules, discovery and backup policy. More machinery than the current need; evaluate before enabling immutable package releases. |
| Actions artifacts / local evidence      | Current release workflow retains artifacts for 30 days; local files depend on the machine.                                                                                                          | Keep detailed logs here. Neither satisfies durable public receipt completion.                                                                                                                                                    |

GitHub documents release management/access and asset limits in [About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), and upload, download, deletion and name-conflict behavior in the [release-assets API](https://docs.github.com/en/rest/releases/assets). The absence of a configured expiry is not a perpetual-retention guarantee. Public visibility, deletion, and account/repository loss remain risks.

[Immutable releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository) cannot accept additional assets after publication. Our GitHub release must be verified before the later docs deployment, so its final docs receipt cannot be uploaded in advance. [Deployment-status retention](https://docs.github.com/en/rest/deployments/statuses#data-retention) and [deployment events](https://docs.github.com/en/rest/deployments/deployments#about-deployments) rule out treating that API as an unrestricted permanent log.

## Facts and ownership

| Reviewed source                                                                           | Observed receipt                                                                                               |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Intended version, compatibility, API behavior, examples, change descriptions and PR links | Registry publication time, dist-tag observation, integrity/provenance and consumer verification                |
| The chosen package commit and inspected candidate identity                                | Resolved remote tag commit, GitHub release ID/URL, draft/prerelease/Latest observations and verification times |
| Docs content, clean canonical source SHA, generated manifest and inspected archive        | Sites source commit, saved version/deployment IDs, deployment time and existing public audience/domain         |
| Static links explaining where publication status lives                                    | Live manifest/changelog matches, browser/readback results, errors, retries and superseding observations        |

The package and docs source SHAs may differ. Record both explicitly; a matching version string does not establish matching source or successful publication. Credentials, authorization headers, user traces, and full command output never belong in public receipts. Record the authorizing request/workflow approval reference only when it is appropriate for public disclosure; otherwise retain that reference privately and publish the resulting job/actor identity.

## Receipt contract and discovery

Introduce schema version 1 with two kinds: `package-publication` and `docs-deployment`. Shared fields identify repository, package/version, event identity, observation time in UTC, producer revision, outcome, and supporting public URLs. Package receipts carry the archive SHA-256/npm integrity, npm timestamp/provenance URL, consumer results, resolved tag SHA, and GitHub release/channel observations. Docs receipts carry the canonical and Sites source SHAs, inspected manifest/archive hashes, Sites version/deployment identity and result, and live/browser verification observations. A docs receipt references the exact package receipt asset ID and SHA-256.

Proposed names are `package-VERSION-SHA256.json` and `docs-DEPLOYMENT_ID-SHA256.json`, with a generated `.md` summary for each. Compute the full SHA-256 over the final UTF-8 JSON bytes; the hash is in the filename and readback report, not recursively inside the JSON. Validate field types, full commit SHAs, supported schema, exact repository/site identity, hash formats, required successful checks, and bounded sizes. A receipt is evidence of observations at its timestamp, not an assertion that Latest or live hosting can never change.

Persist finalized bytes locally before upload. List **all pages** of assets on the exact release ID; never choose the current Latest release implicitly. For the same event identity, compare downloaded bytes and references. An identical existing receipt is a successful retry. A conflicting receipt requires inspection, not overwrite or `--clobber`. A later observation or correction is a new event with a `supersedes` reference to the prior asset ID/hash. Preserve successful history when recording failure or rollback. Parallel conflicting events must be reported as ambiguous rather than selecting whichever upload finished last.

Upload JSON and summary only after validation, then download both through their returned asset URLs and compare bytes/hashes. Check `state: uploaded`; a successful POST alone is insufficient. Store returned IDs, URLs and readback evidence outside the hashed receipt to avoid self-reference. Treat partial uploads as incomplete. Retry the same finalized files, not freshly timestamped substitutes. A `starter` asset left by an upstream failure requires targeted inspection/removal before retry, never deletion of a completed receipt.

Use the exact release page as the stable human entry point; include a “Publication records” explanation in the notes prepared before package publication. Assets remain discoverable even if updating a summary link later fails. Reader tooling must validate the referenced receipts and distinguish package verification, docs verification, stale observations, and incomplete state. Do not infer completion from the existence of a release page or asset filename.

Maintain a second copy of finalized receipts, readback metadata, and inspected archives in maintainer-controlled backup storage outside Actions and the working checkout. Retain it for the supported lifetime of the release, at least as long as its public receipts. Backup location/access and a restore drill must be recorded by the maintainer before rollout; this investigation does not claim such a backup exists. Losing the public asset makes receipt verification incomplete until exact bytes are restored and reverified. If the same store cannot be restored, publish a reviewed replacement-location record, preserving old IDs/hashes.

## Proposed normal path

1. **Prepare once:** merge a reviewed release PR with version/API/compatibility material, stable publication-status links, and green full verification. Static copy says “Prepared release; see publication records for verified status,” rather than making a forever-pending or premature-published claim. The version heading/overview must distinguish preparation from an observed UTC publication date. Existing historical dates remain unchanged.
2. **Publish package:** retain the existing manual dispatch, exact candidate inspection, GitHub environment approval and npm OIDC boundaries. Verify npm/integrity/provenance and fresh registry consumers, then independently verify the exact tag and published GitHub release/channel. Reuse the finish job's existing Contents permission to upload and read back the package receipt; give it no npm OIDC permission. Report “package verified; docs pending” at this point.
3. **Publish docs on explicit request:** choose the intended clean reviewed main commit with green CI, possibly the release commit itself. Verify package receipt and live registry/tag/release observations before presenting released APIs. Build/inspect once, then use the existing manual Sites package/save/deploy workflow. CI does not receive Sites credentials or call deployment tools.
4. **Record docs:** after successful Sites deployment, run live manifest/changelog and browser checks against the retained artifact. Collect the native Sites result and upload/read back its linked docs receipt using the maintainer's existing authorized GitHub session. No source commit or rebuild is needed to insert these newly observed facts.
5. **Finish:** report complete only when both verified receipts are publicly readable, references/bytes match, all independent npm/tag/GitHub/hosting checks passed, and backup capture succeeded. Report any outstanding component explicitly. Do not require a source-receipt PR on this normal path.

The neutral status copy and static links work without JavaScript or unauthenticated GitHub API calls in the docs UI. Network-unavailable readers see an explicit external-status reference, not a fabricated success badge. Updating a historical source summary can be batched into a later substantive PR; it is not required to rewrite the already published snapshot.

### Dry walkthrough

For a hypothetical next version `0.5.3`, preparation commit **R** contains the intended version and status link, but no claimed publication date. The approved archive **A** is published once. npm, consumers, the tag at **R**, and the GitHub release are checked; package receipt **P** is finalized, uploaded, downloaded, hashed and backed up. This is still a partial release because docs are pending.

A reviewed docs commit **D** produces artifact **B**, whose manifest is retained. After the explicitly requested Sites deployment **S** and live/browser verification, docs receipt **Q** references **P** and includes **D**, **B** and **S**. Upload/readback/backup of **Q** completes the release. Neither **A** nor **B** changes, and no post-publication source commit exists. This is a design walkthrough, not an actual `0.5.3` release or remote storage rehearsal.

## Recovery decisions

| Situation                                                            | Required response                                                                                                                                                                                                                                                                        |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| npm upload outcome uncertain                                         | Read the registry first. Verify existing bytes/provenance; never retry publication merely because the client timed out. Resume consumers/tag/release/receipt steps separately.                                                                                                           |
| Tag or GitHub step incomplete                                        | Resolve the existing remote tag and compare the exact approved SHA. Reuse a matching record through recovery tooling; never move the tag or rerun the normal existing-version preflight as a recovery strategy.                                                                          |
| Receipt upload/readback fails                                        | Keep publication verified but completion partial. Retain finalized bytes and inspect existing assets before retrying. A missing summary or failed backup is also explicit outstanding work.                                                                                              |
| Main or Latest advances                                              | Keep the chosen package/docs commits and release ID. Reverify the intended historical channel without downgrading Latest. A new observation records the change; the old receipt remains historical evidence.                                                                             |
| Docs deployment/readback fails                                       | Resume the saved Sites version when appropriate; a failed readback does not authorize a rebuild or another deployment. Record failure separately without implying success.                                                                                                               |
| Docs-only update or rollback                                         | With explicit deployment authorization, inspect the selected artifact, preserve existing access, and append a new receipt under the release matching that artifact's package version. Record the superseded deployment; do not rewrite the previous successful receipt or republish npm. |
| Immutability enabled or target release immutable                     | Do not disable protection. Use the current record-PR fallback and identify this storage limitation before proceeding. A separate store needs its own reviewed rollout.                                                                                                                   |
| Permission denied, missing evidence, conflicting event or lost asset | Stop receipt completion, preserve the evidence, and resolve the narrow problem. Never widen token scopes, invent missing historical observations, or treat an expired Actions artifact as durable proof.                                                                                 |

## Scoped implementation and rollout

1. **Receipt library and fixtures:** add validation, deterministic serialization, collection, event conflict handling, paginated asset discovery and readback, with mocked GitHub/registry/Sites evidence. Reproduce mismatched SHA/hash/site, unknown schema, conflicting identity, interrupted upload, unchanged retry, missing summary and invalid supersession. No runtime exports solely for these tests.
2. **Package integration:** extend `scripts/release.mjs` and its tests to persist all npm/consumer/tag/GitHub observations and attach the package receipt after verification. Keep `workflow_dispatch`, `npm-release` approval, existing permission separation and immutable candidate bytes. Add a separate receipt-only recovery entry point that never calls npm publish, creates/moves tags, changes Latest, or rebuilds an artifact. Keep full candidate/CI checks.
3. **Manual docs integration:** extend the existing publication helpers to validate native Sites evidence and create/upload/read back docs receipts under an explicitly requested publication. Keep Sites deployment manual. Implement failure/retry/rollback records and a read-only status command. Demonstrate that receipt recovery never invokes a deploy operation.
4. **Coordinated policy/content migration:** update release checklist steps 6–7, completion/recovery wording, workflow summaries, docs publishing checklist, changelog preparation/overview guidance, `apps/docs/README.md`, and relevant consumer/installation prose together. Review `apps/docs/changelog.ts`, `apps/docs/build-info.ts`, release-note generation and receipt-scope assumptions against the new static copy; preserve existing deep links and source hashes. Keep historical Markdown receipts. This is a substantive tooling/policy PR and requires full verification, not `verify:receipts`.
5. **Rollout gate before the next patch:** independently review the implementation, run full local and exact-head CI checks, and perform an explicitly authorized storage rehearsal with real upload/download, retry and backup restore on a designated disposable release. Do not mutate an existing published package release as an unannounced test. Recheck immutable-release settings and token permissions; verify public unauthenticated readability, no new deployment listeners/permissions, and retained Sites access. Activate the policy only after these gates pass.

Until implementation and rollout are complete, the existing receipt PRs remain necessary. The smallest fallback is the current constrained `verify:receipts` path for eligible edits; do not skip source review or full CI. The next patch should wait for the rollout gate if eliminating those receipt PRs is a launch requirement.
